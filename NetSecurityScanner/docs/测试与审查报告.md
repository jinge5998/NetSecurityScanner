| 新引擎（`target\release`，哈希 `C14F1A92`） | 含 IPC 连接复用 | 通过，退出码 `0` | UDP 阶段 0.5s / 4 条结果，无重连日志（单连接直接复用） |

### 2.3.2 nmap 工具集完整性核验（2026-11-18）

起因：先前核查时按「nmap 7.x 应随附 `nmap-payloads`」的经验判断，将「缺 `nmap-payloads`」列为待修项。本次按官方 GitHub 仓库（`github.com/nmap/nmap`）与官方发行包双向复核后**确认为误报**，结论如下。

| 核验项 | 方法 | 结果 |
| --- | --- | --- |
| 官方仓库是否含 `nmap-payloads` | 取 `nmap/nmap` tag `7.991`、`7.992` 的仓库文件：`nmap-services` 返回 200，`nmap-payloads` 返回 **404** | **仓库中不存在该文件** |
| 官方仓库 `payload.cc` 实现 | 取 tag `7.992` 的 `payload.cc`（7,384 字符）检索 | 无 `nmap-payloads` 字样；含 `service_scan_init` 与 `notForPayload`，即 payload 索引由 `nmap-service-probes` 构建 |
| 官方发行包是否随附 | 下载官方 `nmap-7.993.tar.bz2`（12,933,292 字节）解包，2,558 个文件中全量检索 | **不存在**；源码中对 `nmap-payloads` 零引用 |
| 官方安装清单 | 查 `Makefile.in` 的 `nmapdatadir` 安装列表 | 仅 `nmap-services`/`nmap-rpc`/`nmap-os-db`/`nmap-service-probes`/`nmap-protocols`/`nmap-mac-prefixes`，无 `nmap-payloads` |
| UDP payload 现由何处提供 | 查 `payload.cc` 的 `init_payloads()` | 由 `nmap-service-probes` 中的 `Probe UDP` 条目构建（`!notForPayload` 过滤），本工具集含 84 条 `Probe UDP` |
| 二进制是否读取该文件 | 检索 `nmap.exe` 内嵌字符串 | 无 `nmap-payloads` 字符串；存在 `nmap-service-probes` |
| 数据文件是否与官方一致 | 逐个 SHA-256 比对 `tools\nmap` 与官方发行包 | **7/7 逐字节一致**（`nmap-services`、`nmap-rpc`、`nmap-os-db`、`nmap-service-probes`、`nmap-protocols`、`nmap-mac-prefixes`、`nse_main.lua`） |
| 运行时是否报缺文件 | `nmap -sU -sV -p 53,123,161 127.0.0.1` | 无 payload / 数据文件告警，53/123/161 均正确识别为 `domain`/`ntp`/`snmp` |

处置：

1. **不补入 `nmap-payloads`**。补入 2022 年版（`vendor\RustScan-2.4.1\nmap-payloads`，63 条 udp）只会让后续维护者误判其为必需文件；nmap 7.993 二进制不含该文件名字符串，无任何读取路径。
2. **发布脚本增加数据文件清单校验**。`rebuild-and-run.ps1` 的 nmap 捆绑段按官方 `nmapdatadir` 清单校验 7 个数据文件 + `scripts/` 目录，缺失时红色 `❌` 提示，避免发布包静默缺失数据文件。
3. **修复发布包 39MB 冗余（新发现缺陷）**。原脚本用 `Copy-Item '*' -Recurse` 整目录复制，把 `nmap-7.993-setup (1).exe`（36.16MB NSIS 安装器）与 `nmap-7.993.tar.bz2`（2.83MB 源码包）带入发布包，运行期完全无用。改为按排除清单复制（`*.tar.bz2`/`*.tar.gz`/`*.tar.xz`/`*.zip`/`*setup*.exe`/`*.lnk`/`*.reg`/`ZENMAP_README`），并对已存在的 publish 目录执行清理。

清理实测（`publish-v1.0.3.10\tools\nmap`）：

| 项目 | 清理前 | 清理后 |
| --- | --- | --- |
| 文件数 | 824 | 819 |
| 体积 | 69.50 MB | **30.50 MB** |
| 移除项 | `nmap-7.993-setup (1).exe` 36.16MB、`nmap-7.993.tar.bz2` 2.83MB、`Zenmap.lnk`、`nmap_performance.reg`、`ZENMAP_README` | 合计 **39.00 MB** |

清理后回归验证：`nmap --version` 正常；`-sT -sV` 识别 `msrpc`/`microsoft-ds`/`ms-wbt-server`；`-sU` 识别 `domain`/`ntp`/`snmp`；E2E 工具退出码 `0`，判定项全 True。

### 2.3.3 NSE 脚本集与官方 `nmap-master`（7.993SVN）对齐（2026-11-18）

起因：用户提供本地完整官方源码仓库 `nmap-master`，要求以其为唯一基准修复专家模式 nmap 引擎。此前仅比对过「是否存在缺失文件」，未比对「同名文件的实现差异」；本次补齐这一层。

**第一步：确立基准版本**

| 核验项 | 证据 | 结论 |
| --- | --- | --- |
| 源码版本号 | `nmap.h`：`NMAP_MAJOR=7`、`NMAP_MINOR=993`、`NMAP_SPECIAL="SVN"` | `nmap-master` = **7.993SVN**（7.993 发布后的官方维护分支） |
| 内置二进制版本 | `tools\nmap\nmap.exe --version` | `Nmap version 7.993`，与基准同主版本 |
| 是否存在 `nmap-payloads` | 全仓库检索 | 不存在，印证 2.3.2 的误报结论 |

**第二步：全量文件比对（`tools\nmap` vs `nmap-master`）**

| 范围 | 数量 | 一致 | 差异 |
| --- | --- | --- | --- |
| 核心数据文件 | 7 | 7 | 0 |
| `nselib/` | 186 | 176 | 10 个中的 4 个 |
| `scripts/*.nse` | 619 | 613 | 10 个中的 6 个 |
| **缺失文件** | — | — | **0（无任何文件缺失）** |

**第三步：10 处差异的影响判定（均为上游缺陷修复，非本地私有改动）**

| 文件 | 上游改动 | 对专家模式的实际影响 |
| --- | --- | --- |
| `nselib\http.lua` | 重定向状态匹配 `^30[01237]$` → `^30[012378]$` | **修复缺陷**：308 Permanent Redirect 不被识别，`http-title`/`http-headers` 等判定为「未跟随重定向」而丢失结果 |
| `nselib\iec61850mms.lua` | `encodeSeq = asn1.ASN1Encoder.encodeSeq` → 包装函数 `function(...) return asn1.ASN1Encoder:encodeSeq(...) end` | **修复缺陷**：直接取方法引用会丢失 `self`，ASN.1 序列编码失败，`iec61850-*` 脚本报错 |
| `nselib\ssh2.lua` | 第三参由 `key_type` 改为 `host_key_algo`；新增 `rsa-sha2-256/512`、`ssh-ed25519`、`ssh-mldsa44-ed25519`；改用 `tableaux.contains` 精确匹配 | **修复缺陷**：现代 SSH 服务端只提供 `rsa-sha2-*`/`ed25519` 时取主机密钥失败 |
| `nselib\tls.lua` | 拆分 `DEFAULT_TLS12_ELLIPTIC_CURVES` 与 `DEFAULT_ELLIPTIC_CURVES` | **修复缺陷**：TLS1.2 ClientHello 不再携带 TLS1.3 专属混合组 `X25519MLKEM768`，避免握手失败与套件枚举失真 |
| `scripts\http-title.nse` | 新增 `status` 字段；标题空白归一化 `string.gsub(..., "%s+", " ")` | 修复含换行/制表符的 HTML 标题输出错乱；XML 增加 `status` 元素便于上层判定 |
| `scripts\ssh-hostkey.nse` | 支持 9 种主机密钥算法，按指纹去重，`pairs` 遍历 | 修复新式 SSH 主机（仅 ed25519）取不到指纹 |
| `scripts\rsa-vuln-roca.nse` | 增加 `rsa-sha2-256`/`rsa-sha2-512` 取键回退 | 修复 ROCA 漏洞在现代 SSH 主机上漏检 |
| `scripts\ssl-enum-ciphers.nse` | 按协议版本选择曲线集（`tls.PROTOCOLS[protocol] < tls13proto`） | 同上 TLS 曲线问题，修复 TLS1.2 站点套件枚举失真 |
| `scripts\broadcast-ping.nse` | `@args` 名 `num_probes` → `num-probes` | 参数名规范化，与 nmap `--script-args` 的 `-` 分隔规则一致 |
| `scripts\nbd-info.nse` | `@args` 名 `export_names` → `export-names` | 同上 |

**发现的 2 个真实问题**

**P1（引擎缺陷，✅ 已修复）：`UdpTimeout` / `ServiceDetectTimeout` 在 nmap 引擎下完全不生效。**

| 核验项 | 证据 |
| --- | --- |
| 界面提供该配置 | `ExpertModeWindow.xaml.cs` 第 845~848 行读取 `UdpTimeoutSlider` / `ServiceDetectTimeoutSlider` 写入 config |
| 契约测试要求其落地 | `ExpertScanConfigEffectivenessContractTests` 第 41、45 行把两者列入「必须到达引擎」清单 |
| Rust/C# 引擎是否使用 | 是，经 `ScanConfigMapper.ToScanProfileConfig` 映射为 `UdpTimeoutMs` / `ServiceDetectTimeoutMs` |
| nmap 引擎是否使用 | 修复前**否**，全文检索 `NmapCommandBuilder.cs` 零引用 |

影响：用户在专家模式调整「UDP 超时」「服务识别超时」两个滑块后，若引擎为 Nmap，两个滑块对实际扫描**无任何作用**，且界面无任何提示。这是三引擎行为不一致。

**修复方案（2026-11-18 已完成）**

nmap 没有与「UDP 超时 / 服务识别超时」一一对应的参数，因此在 `NmapCommandBuilder.AddTimingFlags` 中把它们折算为 RTT 等待上限的下界：

```
rttTimeout = TcpTimeout
  ├─ UdpScan 且 UdpTimeout != 1000（默认值）→ max(rttTimeout, UdpTimeout)
  └─ ServiceDetection 且 ServiceDetectTimeout != 2000（默认值）→ max(rttTimeout, ServiceDetectTimeout)
```

- `--max-rtt-timeout` / `--min-rtt-timeout` 改用 `rttTimeout` 计算
- `--host-timeout` **刻意仍只由 `TcpTimeout` 决定**，不随 `rttTimeout` 收紧（原因见下方 E2E 回归）

设计要点：仅在**用户调整过滑块（非默认值）**时才参与取最大值，因此默认配置下的命令输出与修复前**完全一致**，不改变既有用户预期。

**E2E 实测发现的回归（已修正）**

首版修复曾让 `--host-timeout` 跟随抬升后的 `rttTimeout`（`5000*3=15000ms`）。专家模式 E2E 实测暴露了严重副作用：

| 配置（UDP 扫描 500/udp） | 命令关键参数 | 耗时 | 结果条数 |
| --- | --- | --- | --- |
| 默认滑块 | `--max-rtt-timeout 500ms` | 28.4s | **2** |
| 调大滑块（首版修复） | `--max-rtt-timeout 5000ms --host-timeout 15000ms` | 19.4s | **0** ❌ |
| 调大滑块（修正后） | `--max-rtt-timeout 5000ms`（无 host-timeout） | 29.4s | **2** ✅ |

根因：`--host-timeout 15000ms` 让 nmap 在 15s 放弃主机并输出空 XML，而该扫描实际需 28s 才完成——**用户把超时调大，反而扫不到任何结果**，属于典型的假阴性回归。

修正：`--host-timeout` 属安全兜底，必须比预期耗时更宽松，不能随 RTT 上限收紧。恢复为仅由 `TcpTimeout >= 2000` 触发，值取 `TcpTimeout * 3`。同步新增回归用例 `Build_RaisedRttTimeout_ShouldNotTightenHostTimeout` 与 `Build_RaisedRttTimeout_ShouldKeepHostTimeoutFromTcpTimeoutOnly`。

**修复验证**

| 单元测试 | `NmapCommandBuilderTests` 73 个用例全部通过，新增 8 个接线/回归用例 |
| 契约测试 | `ServiceDetectTimeout_ShouldReachEngine` 由旧断言 `Be`（固化「对 nmap 无效」）改为 `NotBe` + 断言 `--max-rtt-timeout 10000ms` |
| 全量回归 | **337/337 通过**，无失败 |
| 整体编译 | `dotnet build src/NetSecurityScanner.sln` 成功 |
| 真实 nmap 接受度 | `--max-rtt-timeout 5000ms --min-rtt-timeout 1000ms` 退出码 `0`，无 `unrecognized option` |
| 执行器透传 | `NmapEngineExecutor` 的剥离白名单仅含端口/速率类参数，时序参数原样下发 |

**P2（环境因素，非引擎缺陷）：UDP 扫描 IKE 相关端口固定耗时约 100s。**

| 实验 | 命令 | 耗时 |
| --- | --- | --- |
| 对照（无 IKE 端口） | `-sU -sV -p 53,123,161` | **2.6s** |
| 含 4500 | `-sU -sV -p 4500` | **102.6s** |
| 含 500 | `-sU -sV -p 500` | **117.5s** |
| 纯 UDP 无 `-sV` | `-sU -p 500` | 3.4s |
| 加 `--max-retries 1 --max-rtt-timeout 200ms` | `-sU -sV -p 500` | 116.6s（**无效**） |
| 加 `--host-timeout 3s` | `-sU -sV -p 500` | 8.6s（被跳过主机） |

根因：nmap 的 isakmp probe 需绑定源端口 500 发起 NAT-T 探测，而本机 `500/udp` 已被 `svchost`（PID 5052）占用，`mksock_bind_addr()` 返回 `WSAEACCES (10013)`，nsock 重试约 100s。`--max-retries` / `--max-rtt-timeout` 均无法缩短该 bind 重试，只有 `--host-timeout` 能截断。

判定：这是 **nmap 在 Windows 上的固有行为 + 本机端口占用**，不是工具集或引擎代码缺陷，也不影响扫描结果正确性（4500 仍正确识别为 `nat-t-ike`）。但引擎侧当前无 `--host-timeout` 兜底（`NmapCommandBuilder` 仅在 `TcpTimeout >= 2000` 时输出），默认配置下用户会看到约 100s 的「无响应」期。

**P3（提示噪音，无需处置）**：`--script safe` 输出 `Bug in broadcast-upnp-info: no string output.` 与多条 `Windows does not have adequate raw socket support.`。这是 `broadcast-*` 系列脚本在无 raw socket 权限时的固有提示，退出码 `0`、NSE 其余 116 行输出正常。

**处置建议**

| 问题 | 建议 |
| --- | --- |
| P1 | ✅ **已完成**：在 `AddTimingFlags` 中以 `UdpTimeout`（UDP 扫描时）/ `ServiceDetectTimeout`（服务识别时）抬升 `--max-rtt-timeout` 下界，取最大值语义；`--host-timeout` 保持只由 `TcpTimeout` 决定 |
| P2 | ⚠️ **不处置（有意保留）**：`--host-timeout` 一旦收紧到 15s 级别就会截断本可完成的扫描并产生 0 条结果（已由 E2E 实测证实）。该慢速现象是 nmap 在 Windows 上 IKE 探针 bind 重试的固有行为 + 本机端口占用，属环境因素，且扫描结果本身正确。引擎侧已有 `CancellationToken` 兜底，不会无限挂起，故不为它牺牲正确性 |
| P3 | 不处置。属上游脚本在受限权限下的正常提示 |

**行为差异（非缺陷，两引擎结果语义不同，已用 `Diff` 单独记录）**

| 差异 | nmap 引擎 | 内置 C# 引擎 | 判定 |
| --- | --- | --- | --- |
| 结果集范围 | 回传全部端口状态（含关闭） | 只回传命中状态（开放 / 开放或过滤） | 设计选择，开放端口集一致即可 |

| 取消 | 必须 kill 子进程 → 抛 `OperationCanceledException` | 返回已扫到的部分结果（Task 正常完成） | `ExpertModeWindow` 依赖该特性在取消后展示已扫结果 |

**关于内置引擎取消路径的结论（不修改）**

`PortScanner` 顶层 `catch (OperationCanceledException)` 确实 `throw`，但每个端口的内部 `catch` 会返回 `null`，使任务以 `RanToCompletion` 结束，因此取消时通常不抛异常、而是返回部分结果。若改为强制重抛，`ExpertModeWindow` 的 `ContinueWith(... RanToCompletion ...)` 将丢弃已扫结果、用户取消后看不到任何数据。故保留现状，按上述「行为差异」登记，不视为缺陷。
