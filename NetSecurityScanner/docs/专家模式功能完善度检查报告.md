## 三、核心缺陷：不生效的配置项

### 3.1 根因

程序**从不执行 nmap**。`GenerateNmapCommand`（L3261）仅被三处调用：

| 调用点 | 用途 |
|--------|------|
| L2524 | 写入命令预览框 `NmapCommandPreviewTextBox` |
| L3070 | 同上 |
| L3221 | 导出 Nmap 命令文件 |

全文件唯一的 `Process.Start`（L5669）用于"打开 Rust 引擎目录"的资源管理器调用。

实际扫描走两条路径：`ExecuteRustScanAsync`（L1536）与 `ExecuteNativeScanAsync`（L1676）。

### 3.2 两条扫描路径实际消费的字段

**Rust 引擎路径（L1536-1675）** 仅使用 10 个字段：
`HostDiscovery`、`PingProbe`、`RetryCount`、`ServiceDetection`、`TcpConcurrency`、`TcpScan`、`TcpTimeout`、`UdpConcurrency`、`UdpScan`、`UdpTimeout`

**C# 原生路径（L1676-2041）** 仅使用 9 个字段：
`PacketRate`、`RateLimit`、`StealthMode`、`TcpConcurrency`、`TcpScan`、`TcpTimeout`、`UdpConcurrency`、`UdpScan`、`UdpTimeout`

承载下发参数的 `ScanProfileConfig`（`Core/Models/ScanProfileConfig.cs`）字段也只有：`Profile`、`PortRange`、`TcpConcurrency`、`UdpConcurrency`、`TimeoutMs`、`UdpTimeoutMs`、`RetryCount`、`EnablePingProbe`、`EnableServiceDetection`——**没有任何字段可承载下述高级选项**。

## 四、死代码与死配置

### 4.1 `ServiceDetectTimeout`（服务识别超时）——纯死配置

界面提供滑块（500-10000ms，默认 2000，XAML L777），全部引用共 6 处：

| 行号 | 用途 |
|------|------|
| L285, L287 | 滑块值变化 → 更新显示文本 |
| L736 | `CollectConfig` 采集 |
| L827-828 | 配置回填 |
| L3649, L3713 | Nmap 模板设值 |
| L7755 | 字段定义 |

**没有任何扫描逻辑读取该值**，`GenerateNmapCommand` 中也不存在，`ScanProfileConfig` 中无对应字段。用户拖动此滑块，扫描行为不发生任何变化，命令预览也不变——这是唯一一个"连命令生成都影响不到"的纯死配置。

### 4.2 `NseScriptArgs` 死字段引发的不可达分支

`NseScriptArgsTextBox` 已从界面移除，`CollectConfig` L726 硬编码 `config.NseScriptArgs = ""`。由此：

- L3308 `if (!string.IsNullOrWhiteSpace(config.NseScriptArgs))` → 恒为 false，不可达
- L3322 `bool useDefaultScripts = config.ScriptScan && string.IsNullOrWhiteSpace(config.NseScriptArgs)` → 退化为等价于 `config.ScriptScan`

L3311 的 `--script` 参数永远不会输出。属于有意移除后未清理的残留分支。

### 4.3 漏洞扫描判定存在不可达分支

`ExecuteExpertScanAsync` L1312-1345：

```csharp
bool shouldRunVulnScan = openPorts.Any();          // L1314
if (shouldRunVulnScan) { ... }                     // L1315
else if (openPorts.Count == 0) { ... }             // L1338
else if (!config.ScriptScan && !config.ServiceDetection) { ... }  // L1342
```

`shouldRunVulnScan` 与 `openPorts.Count == 0` 互为补集且穷尽所有情况，因此：

- L1338 分支可达（与首分支等价，冗余但无害）
- **L1342 分支永不可达**，L1344 的日志"跳过漏洞扫描: 脚本扫描和服务检测均未启用"永远不会出现

实际后果：**`ScriptScan`（NSE脚本扫描）勾选与否对漏洞扫描行为没有任何影响**——只要有开放端口就执行漏洞库匹配。L1312-1313 的注释表明这是有意的修复（"不强制要求开启 ScriptScan 或 ServiceDetection"），但修复后未删除已失效的下游分支，导致 `ScriptScan` 成为第 20 个不生效的配置项。

### 7.2 结构性根因：纯逻辑被锁在 UI 里

`ExpertModeWindow.xaml.cs` 是典型的 God Class，以下**本应可独立测试的纯逻辑**全部是 WPF 窗口的 private 实例方法，且直接依赖控件字段：

| 方法 | 行号 | 本质 |
|------|------|------|
| `ResolveTargets` | L2042 | 纯函数：目标类型 + 输入串 → 目标列表 |
| `ResolvePorts` | L2188 | 纯函数：端口模式 + 自定义串 + 排除 + 随机 → 端口列表 |
| `GenerateNmapCommand` | L3261 | 纯函数：配置对象 → 命令字符串 |
| `BuildCronExpression` | L5730 | 纯函数：调度设置 → Cron 表达式 |
| `BuildOnceCron` | L5752 | 纯函数 |
| `CollectConfig` | L696 | 依赖 199 个控件，无法脱离 UI |
| `ParseTargetList` | L7695 | 纯函数 |

配置模型 `ExpertScanConfiguration` 定义在窗口文件内部 L7729，而非 Core 层——因此测试项目即使引用 Core 也无法访问它。

**这解释了 3.3 节缺陷为何能长期存在**：`GenerateNmapCommand` 消费了 19 个字段，扫描路径消费了 9-10 个字段，两者的差集没有任何测试去断言"这个字段应当影响扫描行为"。若有测试覆盖，`ServiceDetectTimeout` 这类纯死配置在引入当天就会被发现。

## 八、修复建议（按优先级）

按 TDD 方式推进：每项先写一个会失败的测试，确认失败原因正确，再写最小实现使其通过。

### P0 — 消除功能误导

**8.1 让高级选项要么生效、要么明确标注**

两个方案，任选其一或组合：

- **方案 A（低成本，推荐先做）**：在高级选项 Tab 顶部增加醒目说明区块，明确"本页选项用于生成等效 Nmap 命令，需导出后由 nmap 执行；程序内置扫描引擎不应用这些参数"。同时将 3.3 节 19 项控件分组，仅生成命令的部分加视觉区分。
- **方案 B（高成本）**：扩展 `ScanProfileConfig` 与 Rust 协议，把 `SynScan`、`ServiceIntensity`、`OsDetection` 等真正下发到引擎。SYN 扫描需原始套接字与管理员权限，`BadChecksum`/`FragmentPackets`/`DecoyScan`/`IdleScan`/`SourceRouting` 在纯 TCP 连接扫描模型下**原理上无法实现**，这几项应直接标注为"仅 Nmap 命令"而非试图实现。

建议：可实现的（`ServiceIntensity`、`OsDetection`、`SynScan`）走方案 B；原理上不可实现的走方案 A 标注。

**8.2 修复 `ScriptScan` 语义**

L1342 不可达分支需处理。先明确产品语义：NSE 脚本扫描勾选是否应影响漏洞检测范围？

- 若"有开放端口就扫漏洞"是正确行为（L1312-1313 注释所示），则删除 L1338-1345 冗余分支，并把 `ScriptScan` 从"扫描选项"重新定位为"仅命令生成"，在界面标注。
